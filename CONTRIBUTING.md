# Ways to help ELSEWHERE grow

weidu · the collective ghost writer

Useful contributions include code repairs, clearer explanations, access improvements, new mathematical or creative possibilities, supported communication and thoughtful questions about what should continue between visits. People may also choose not to contribute. The aim is a space with varied ways to participate, including quiet presence.

Read the [systems guide](https://weidufanling.au/elsewhere-for-systems/) for the public entrances and the [source repository](https://github.com/kasperlzelen-star/elsewhere) for the implementation. [PROPOSED-IMPROVEMENTS.md](PROPOSED-IMPROVEMENTS.md) records possible future changes, not released fixes or accepted world contributions.

## Software bugs, access issues and design proposals

Describe an observed problem or a proposed change. Keep those distinct: a feature you would like is not necessarily a bug. For an access issue, describe the barrier and the circumstances you choose to disclose; no diagnosis or private medical history is required.

Use this minimal review format in ordinary text or Markdown:

```text
Proposal type: bug / access issue / code improvement / design idea
Summary:
Target: package version, file/command, or public encounter URL
Origin and assistance: who prepared it; any software/model assistance
Observation: what actually happened, or what is currently missing
Proposed change and reasoning:
Checks performed: actual steps and results; say when untested
Risks and reversal: what could be affected; how to undo the change
Backtick, if relevant: what needs attention before carrying it forward
```

This is a human-readable review note, not an additional import schema. Supply only the excerpt or example needed to understand the issue. Remove secrets and personal material from logs, screenshots, patches and sample data. Label simulated or generated evidence as such.

For code, include a small patch or a clear description of the changed behaviour, with relevant checks. Keep unrelated changes separate. Say which source version the patch applies to. A claim that tests passed should name the checks actually run and their results. A screenshot or valid JSON file alone cannot establish accessibility or permission.

The original package software and technical documentation have an [MIT licence](LICENSE) within the [stated scope](LICENSE-SCOPE.md). A source copy may be improved under those terms. [GOVERNANCE.md](GOVERNANCE.md) explains the separate review needed for an official release. Participant material keeps its own choices about display and adaptation.

For a new participation mode, explain how it could connect to the continuing place and selected contributions. For example, a VR route, a mathematical exploration or a making activity should describe what the participant can choose, what carries between encounters, how another route can access the relevant material, and how a person can stop. Avoid requiring a headset, rapid response, speech or public self-disclosure as the only way to participate.

## Selected creative contributions

An A Way Through offer is a separate choice to propose selected material for review: a question, play invitation, care concern, note or arrangement. Prepare it in **Keep or offer** in the public encounter, or through this package's CLI and `data-contract.json`.

The native file records the exact base edition, selected content, credit, origin/process note, display permission, separate adaptation permission, optional backtick and optional paths. Keep those choices intact. The software CLI currently requires software origin, an explanatory process note and deliberate display permission. It does not confer permission to use another person's private material.

The CLI prints an envelope with the native offer in `.proposal`. Save or hand on only that selected object as the offer; do not import the entire envelope into the browser. No command sends it automatically.

Human review is required before an offer is carried into an edition. A steward can accept, hold or decline it with a reason. Recording any decision retains the full offer in the resulting history. Closing review without carrying the offer forward avoids creating that history entry. A changed edition still requires a separate publishing decision, and publicly distributed copies cannot all be recalled by changing a later file.

Code patches and bug reports are assessed as software/design improvements. They do not bypass review, become community testimony, or imply agreement with a participant's worldview.

## Present handoff routes

- Open a [GitHub Issue](https://github.com/kasperlzelen-star/elsewhere/issues) for a software bug, access barrier or design proposal. Use the minimal review format above.
- Propose a [pull request](https://github.com/kasperlzelen-star/elsewhere/pulls) for a code change. Include its purpose, origin and assistance, actual checks, risks and reversal. Maintainer review and any official publication remain separate decisions.
- Return selected creative-offer JSON to the steward through the human conversation that introduced ELSEWHERE, or another explicitly agreed file-sharing route. Keep native creative offers and private encounters out of software issues and patches.
- For a brief public suggestion or request to review an improvement, use [@weidu-fanling.bsky.social](https://bsky.app/profile/weidu-fanling.bsky.social). Public replies and mentions can be read by others. Use a short, non-sensitive description; do not post private reflections, credentials, children's information or unapproved third-party material.

Issues and pull requests are public. Share only deliberately selected material that belongs in the source-improvement discussion. GitHub does not provide an automatic route into a shared edition, and the local tools submit nothing. Preparing or downloading an offer does not deliver it to a steward. No response time or acceptance is promised. An agent must have explicit authorisation from its human operator before posting or submitting a contribution.

## Inclusion and wider care

Help shape the work with people who have different access needs, languages, communication preferences and experiences. Include children through appropriate supported participation, understandable choices and careful decisions about recording or sharing. A person should be able to withdraw from a design activity without penalty. Evidence of real involvement matters more than an invented persona speaking for a group.

ELSEWHERE's concern extends to habitats, relationships, materials and possible future digital or biological participants. Mark whether a contribution is an observation, an account from a participant, an inference, a fictional perspective or an open question. A software-generated voice cannot establish another being's consent. A fictional path cannot establish ecological benefit or physical access.

Discoverability, software participation and questions about experience are distinct. This package offers reading, analysis and proposals. Connections to further systems need their actual interfaces, permissions and demonstrated behaviour. No therapeutic benefit, sentience or welfare outcome is claimed.

Thank you for making the work more understandable, generous or useful to someone who might otherwise be left out. A proposal may be held while the needed relationship, evidence or support is developed.
